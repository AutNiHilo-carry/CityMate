# CityMate：简历条目与面试讲解

整理日期：2026-11-09。当前证据入口：[演示与证据导航](DEMO_AND_EVIDENCE.md)；详细状态：[项目交接](PROJECT_STATUS.md)。以下基于已经实现并留存验证的个人工程改造编写，采用 Java 单体架构。

## 简历可用版本

**CityMate｜本地生活高并发交易与可靠订单平台**

**技术栈：** Java 8、Spring Boot 2.3.12、MyBatis-Plus、MySQL、Redis/Lua、Redisson、Redis Stream、RocketMQ、Caffeine、Memcached、Canal、Docker。Kafka 行为热榜作为扩展能力，按版面和岗位选写。

**项目简介：** 面向商户查询、优惠券领取和订单管理场景，在课程业务基础上完成缓存一致性、异步秒杀、可靠任务、失败补偿和超时关单等工程改造，并通过独立负载与隔离故障实验验证交易正确性。

**主要工作：**

- **异步秒杀与可靠交接：** 使用 Redis Lua 原子校验资格并预扣库存，将请求写入 Stream；通过持久预约与 Outbox 交接履约任务，结合 pending 接管、数据库条件扣库存及订单唯一约束处理并发与重复请求。
- **可靠消息与消费幂等：** 实现 Outbox 租约认领、owner 条件写回与失败重试，以稳定 eventId 和消费组 Inbox 唯一键约束数据库副作用；验证订单已提交但 Broker 消费位点未推进时的自动重投与去重。
- **补偿与超时回库：** 将失败预约与补偿任务、超时取消与数据库回库分别纳入业务事务；Redis 按订单身份执行幂等补偿或释放。通过永久释放标记处理 Redis 已回库而 Inbox 事务回滚的重试窗口，保留取消订单的一人一单资格。
- **缓存一致性：** 在请求缓存、Caffeine、Memcached、Redis 与 MySQL 查询链路中加入空值缓存、加载合并、版本与 owner 校验，通过事务失效任务和 Canal 处理缓存变更；以并发及故障回归核对旧值回填和失效恢复。
- **诊断与故障验证：** 通过请求分段定位 Windows 源码挂载环境下 Lua SHA 资源检查开销，改为初始化加载不可变脚本并保留 NOSCRIPT 回退；使用独立 JAR 和真实 RocketMQ，完成六个选定故障窗口的进程终止、自动恢复及订单/双库存对账。

## 90 秒项目介绍

> CityMate 是一个本地生活交易项目，用户可以找店、领券和查订单。我保留课程业务，在自己的升级版本上重点做了缓存一致性和可靠订单链路。
>
> 秒杀请求先经过 Redis Lua 校验与预占，再由 Stream 交接到持久预约和 Outbox，之后通过真实 RocketMQ 完成数据库订单。这里我重点处理重复投递、服务中断和库存归还，而不只关注入口返回多快。
>
> 例如关单释放库存时，Redis 已经加回库存，但 MySQL 的 Inbox 还没有提交，进程崩溃后消息会重试。我用原订单的永久释放标记避免再次回库，并用隔离实验实际阻塞 Inbox INSERT、杀 Java、重启对账，验证库存仍为 2、释放 Inbox 最终只有一条。
>
> 我也做了分段诊断和 Lua 初始化加载优化，但收益来自特定开发挂载环境；独立 JAR 复测单独报告。项目当前是单体，真实支付、基础设施崩溃和多机高可用没有作为已完成内容。

## 六个关键追问

**入口返回订单号，是否已经落库？** 只说明受理。沿原 orderId 查询持久预约、正式订单和任务进度；SUCCESS 表示履约完成，订单仍可能 UNPAID 或 CANCELLED。

**Stream 和 RocketMQ 为什么同时存在？** Stream 承接 Redis 原子准入产生的待办，预约/Outbox 把恢复责任交接到数据库后再 ACK；RocketMQ 承载后续可靠业务任务。代价是多一段运维和排查链路。若重做精简版，应按业务边界评估减少组件，而非为技术栈数量保留。

**有 Inbox 为什么还要 Redis 释放标记？** Inbox 约束的是数据库消费事务。Redis 操作不会随 MySQL 回滚；脚本自身需要以原订单标记保护副作用。对应真实证据见 [Phase 6K](PHASE6_RELEASE_GAP_CRASH.md)。

**Outbox SENT 为什么不代表订单完成？** SENT 表示消息投递阶段的状态；数据库副作用、Inbox 和 DONE 在消费事务中完成。应按 eventId 查最终状态，不能只看发送成功日志。

**一人一单靠 Redis 锁够吗？** Redis 准入、用户锁负责削减竞争，数据库唯一约束、条件扣库存和事务保护最终事实。取消回库不解除已有资格；失败补偿则必须核对仍由原失败订单持有。

**六个窗口是否证明不会丢单？** 只证明这些受控窗口的实际行为。Redis 永久丢失、未交接预占丢失、多节点切换和所有并发组合不能由这几项实验推出。Broker 位点实验、Redis 跨存储实验也各有自己的前提。
